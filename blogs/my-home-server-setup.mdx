Over the last few months, I've been gradually building a **home server** that I actually *use* every day. Why? You may ask, basically to be free of the usual internet (and also because Gilfoyle from silicon valley conviced me to build my own Anton).

![Gilfoyle at his desk in Silicon Valley, captioned: "To get rid of all the bugs was to get rid of all the software. Which is technically and statistically correct."](/gilf.png)

*The man who radicalised me. I have taken the opposite lesson and added more software.*

This blog walks through **why I built it, what I'm running, and how everything fits together**.


## Why I Built a Home Server

A VPS gives you a shell and a bill; it doesn't give you the machine. On AWS or GCP the interesting parts, the disk, the NIC, the router in front of it, are abstracted away behind a console, and when something breaks you file a ticket instead of learning something. I wanted the layer underneath, plus a place to break things without a billing alert as punishment.

It also turned out to be the fastest way to actually learn networking, Linux and Docker. Not tutorial-learning, where you copy commands into a terminal and everything works. The kind where DNS is broken at 1 AM and nobody is going to fix it for you.

And most importantly: a media server. I was tired of paying for four streaming platforms that between them still didn't have the thing I wanted to watch that night.


## Hardware

The whole thing runs on a beat up **2018 Lenovo IdeaPad 5** that I bought in my first year of college for under 60,000 INR (~$650). 8GB of RAM, soldered, which I found out the hard way when I went looking for an upgrade slot and found none. 512GB SSD.

Thin for a server, but a laptop makes a surprisingly good one: built-in UPS (the battery), a few watts at idle, silent, and the lid closes so it lives on a shelf instead of my desk. I did have to tell systemd to ignore the lid switch, otherwise closing it suspends the machine and takes every service down with it. My server kept falling asleep on the job. Relatable, but not acceptable. One line in `/etc/systemd/logind.conf`:

```
HandleLidSwitch=ignore
```

The 8GB is the real constraint and it shapes everything below: no VMs, no Kubernetes, no service that idles at a gigabyte. It's been running 24/7 since, without noticeable heat, fan noise or a dent in the power bill.


## Operating System & Base Setup

I'm running **Debian 12**, chosen mostly because it's boring. Stable packages and nothing that surprises me during an update. The base setup came down to five things:

1. **No desktop environment.** A netinstall with only the standard utilities, saving a few hundred MB of RAM I don't have to spare.
2. **Key-based SSH on a non-default port,** password login disabled in `sshd_config`. The port change isn't real security, it just cuts the bot noise in the logs down to almost nothing.
3. **Firewall enabled, default deny.** Only SSH and the reverse proxy are open inbound.
4. **Automatic security updates** via `unattended-upgrades`, restricted to the security repo so nothing quietly changes behaviour on me.
5. **fail2ban** watching the SSH log, for the few bots that do find the new port.

Keeping the host minimal means there's very little on it I have to reason about when something goes wrong. The interesting state lives in containers.


## Containerization with Docker

Everything runs in **Docker**, managed with Compose. Each service gets its own compose file and directory, with volumes bind-mounted to a known path, so config and data are always somewhere I can point a backup at.

Docker earns its place for isolation, upgrades that are a `pull` and an `up -d` instead of a negotiation with apt, and rollback that takes about fifteen seconds when a new image breaks something. The compose file also ends up being the only documentation I need. On 8GB the overhead is real, so the rule is one service per container and nothing running "just in case".


## Services I'm Running

### 1. Reverse Proxy & SSL

Everything sits behind one reverse proxy. It terminates TLS with automatic renewal, so I've never manually touched a certificate, and routes by subdomain: one public entry point fanning out to a dozen services, each on a hostname instead of a port number I'd have to remember.

### 2. Home Automation

Home Assistant controls all my lights, WLED strips and Matter devices, and the ESP-based bits I flashed myself. I automated the lights so I'd never touch a switch again, then spent six hours on my phone touching a picture of a switch.

### 3. Media

The idea of owning your own media? Hell yeah. So the second thing I installed was Jellyfin, along with the *arr services and a qBittorrent client (for finding and reading books, obviously). Jellyfin has to transcode on an ageing laptop CPU, which it is not thrilled about, so I keep direct-play formats where I can.

The app I love most these days is [Seer](https://github.com/seerr-team/seerr). It gives everyone else in the house a request button instead of a message to me. I built an entire media platform to avoid a conversation, which I consider a good trade. Screenshots below.

### 4. Monitoring & Logs

System metrics, container health checks, and logs centralized in one place so debugging doesn't mean SSH-ing around reading four different files. On 8GB, the memory graph is the one I actually watch. It's the first thing to tell me a new service was a bad idea.


## Networking & Remote Access

My ISP doesn't hand out static IPs, and like most home connections here it's behind CGNAT, so port forwarding was never going to work. I learned what CGNAT was at roughly the same moment I learned it was my problem. Dynamic DNS keeps a hostname pointed at whatever address I have, and a reverse tunnel handles outside access: the server dials out to a small public endpoint and traffic comes back down that connection.

Nothing is exposed without authentication in front of it, which occasionally means logging in twice to check whether a download finished. Worth it.


## Backups & Data Safety

One rule: **assume the disk will fail**. It's a seven-year-old SSD in a laptop that never turns off, so this is arithmetic, not paranoia.

Nightly jobs copy everything to a secondary drive, config and compose files are version-controlled, and anything sensitive is encrypted before it's written. The media library is excluded, because it's large and replaceable.

A backup you have never restored is not a backup, it's a hobby. I've timed mine: rebuilding from a blank Debian install takes under an hour, most of it waiting on downloads.


## What I Learned

Linux internals, because there's no managed service to hide them. Real networking: NAT, DNS, ports, and why CGNAT ruined my first weekend of plans. Docker, past the point of copying compose files off the internet. And that every convenience you add is a door you have to think about.

Also that it's always DNS. I did not believe this before. I believe it now, the way people believe things after an incident.

Most importantly, it gave me **confidence**. I know exactly what's running, where my data lives, and how to fix things when they break.

## Final Thoughts

A home server isn't about replacing the cloud.
It's about **understanding it**.

If you're a developer who enjoys building systems end-to-end, I highly recommend setting one up. Start small. Break things. Learn fast.
