# Why a Text-to-SQL Agent?

Someone in finance was spending about eight hours a week writing the same *shapes* of SQL by hand, with a different vendor or quarter each time. That's the situation a dashboard can't fix: a dashboard answers the questions you thought of in advance, and has nothing for "payables for this vendor, this quarter, excluding cancelled."

So, not AI for finance. Deleting a chore that happened to be a translation problem. Two systems came out of it: a change data capture pipeline that turns transactional data into something an LLM can query, and a reporting agent on top. The second only works because of choices made in the first.

---

## Part 1: Why change data capture

The obvious way to feed the agent is a nightly job that dumps production into a warehouse, and that approach is genuinely good. A batch dump is idempotent by construction. If it fails, you rerun it. No offset state to corrupt, no consumer group to rebalance, no replication slot quietly filling your disk at 3am. The failure mode is "the job didn't run," which is loud.

We used CDC anyway, for exactly one reason: freshness. "What are our payables this week" means this week, not as of last night. Once the answer can change between when the pipeline ran and when the question was asked, batch is done. That's the whole trade, and if an hour stale had been fine I'd have written a cron job and gone home.

### How CDC works

![How change data capture works: a write-ahead log holding a sequence of insert, delete and update records feeds a CDC process, which lands changes in a staging area and then into the target system, with a transform step spanning the flow](/diagrams/cdc.webp)

CDC reads the write-ahead log and emits an event for every insert, update, and delete. Because the WAL is what the database already uses for durability, you get every change without polling and without touching the query path.

For Postgres, Debezium doesn't read the raw WAL. It goes through logical decoding via a replication slot, which turns physical WAL records into row-level changes. That distinction matters at 3am: a replication slot holds WAL on the primary until the consumer confirms it read them, so a consumer that dies quietly grows the WAL until the disk fills. The mechanism that makes CDC reliable is the same one that can take down your primary.

### The bug that throws no exception

Delivery is at-least-once. On a restart or a rebalance you get the same event twice, and in financial data that's a payable counted twice. The fix is easy: unique key per table, upsert instead of insert, and a repeat becomes a no-op.

That handles duplicates. Ordering is the one that hurts.

![A balance moving 100 to 200 to 300 as events e1, e2, e3 with LSN 1001 to 1003. Event e2 is redelivered after e3. Upserting by key alone writes 200 over 300 with no exception and no alert, leaving the row silently stale. Upserting with the LSN guard compares stored 1003 against incoming 1002, updates zero rows, and 300 survives](/diagrams/ordering-bug.svg)

A balance goes 100, 200, 300. Event two gets redelivered after event three already landed, so you upsert by key, see the older event, and write 200 over the 300. Nothing crashes. No exception, no dead letter queue, no alert. The row is just wrong until it happens to change again, and meanwhile the agent reports a balance that was true twenty minutes ago.

So make the write conditional on the incoming event being newer. My first instinct was `updated_at`, which is the right idea with the wrong clock: it's application data, trustworthy only if every write path sets it correctly on every table forever, which lasts right up until someone runs a manual UPDATE in production.

Use the log sequence number instead. Debezium puts it in every event's `source` block, it's the position in the WAL where the change committed, and it's monotonic by definition.

```sql
UPDATE flat_table
SET ..., _lsn = :incoming_lsn
WHERE key = :key
  AND _lsn < :incoming_lsn;
```

We also shipped without handling deletes, then found rows sitting in the flat tables after being removed upstream, which meant the agent was confidently reporting on money that no longer existed. Deletes need the same guard, or a redelivered delete wipes a row that was legitimately recreated.

### Flattening

The consumer doesn't write a normalized replica. It writes denormalized tables, pre-joined and shaped for reporting. This felt like a convenience at the time. It turned out to be the most important decision in either system, for reasons that show up in Part 2.

## Part 2: The reporting agent

![The reporting agent pipeline: a question is embedded and matched to the nearest golden query, then SQL is generated, then a second model judges the generated query against the golden one, then Postgres executes it and returns the number. A question with no near neighbour branches off, flagged as novel and answered ungated](/diagrams/agent-pipeline.svg)

First question: where does the arithmetic happen? If the LLM reads rows and adds them up, you're trusting a language model to do maths over a large context, which is the thing they're worst at. So the agent writes SQL, Postgres does the math, and the model never touches a number.

That kills an entire category of failure. It does not kill the interesting one.

### The failure that looks like success

The model doesn't hallucinate the arithmetic. It hallucinates which query to write. A question about payables due this quarter comes back filtering on `created_at` instead of `due_date`. Or missing the status filter, so cancelled items are in. Or joined in a way that double counts.

The SQL is valid. It runs. It returns a clean, confidently formatted, completely wrong number. There's nothing to catch, because nothing failed.

This is where flattening pays off. `SELECT SUM(amount) FROM payables WHERE due_date BETWEEN ... AND status != 'cancelled'` leaves very little room to be wrong. The same question against a normalized schema means reasoning about five table relationships, and every join is a fresh chance to double count. The most effective reliability work here wasn't prompt engineering, it was schema design.

### Coverage is not correctness

We keep a golden query suite, about a hundred entries, growing as people use the agent. Each is a question plus a vetted, human-written query. New questions get embedded and compared by cosine similarity: close to something we have, treat it as covered; far from everything, flag it for a human.

Then I spent a while believing this meant more than it does.

![Two separate boxes. The coverage check takes the question as input and asks whether a test exists for it. The correctness check takes the generated SQL and returned number as input and asks whether this particular run was right. The two never touch each other](/diagrams/coverage-vs-correctness.svg)

The similarity check looks at the question. It never looks at the generated query or the number that came back. A run can be marked covered and still be wrong.

### An LLM judging an LLM

There's a second node: after the agent writes its query, we hand it and the nearest golden entry to another model to judge whether they're consistent, and flag failures for regeneration.

It helps, but take the `created_at` versus `due_date` bug. That query is semantically almost identical to the correct one. Same tables, same shape, same aggregate, one predicate different. A judge whose idea of "close" is semantic sees a match, because semantically it *is* one. The difference is business logic, which barely moves the meaning and completely changes the number.

The judge fails in exactly the cases the generator failed, because they think the same way. A verification layer that's wrong precisely when you need it isn't a guarantee. It's a colleague who agrees with you.

### What would actually catch it

![A table of four checks. The LLM judge catches drift but shares the generator's blind spots, and it is the one we have. Execute and compare, SQL lint rules, and reconciliation invariants all catch drift without sharing those blind spots, and all three are missing](/diagrams/checks-matrix.svg)

The checks that work are the ones a language model can't talk its way around. **Execute and compare** runs both queries and compares values rather than text. **Structural assertions** lint the SQL: a payables query must filter on status, a period query must filter on the date column that means "due." **Reconciliation invariants** are arithmetic the numbers have to satisfy regardless of how they were fetched, like subtotals summing to totals.

Any one of these catches the bug both models miss. We have none of them. Reconciliation invariants are what I'd add first.

There's one hole none of it closes. A genuinely novel question has no near neighbour, so there's nothing to compare against. It gets answered live, flagged, and a human writes the golden entry afterwards, which means the first run of every new report type is ungated by design. At a growing company that isn't an edge case, it's a steady drip.

The systems work and people use them every day. They're also less verified than the confidence of their output suggests.
