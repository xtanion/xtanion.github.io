# Distributed Task Processing

The short version: we had an Express.js API sitting on PostgreSQL, and a growing pile of work that had no business happening inside a request. I built the system that moved that work off the request path, made it searchable, and made it observable.

Throughput went up about 40%. Most of that did not come from the queue itself. It came from finding out where the time was actually going, which took longer than the building did.

## The Awkward Part: Node in Front, Python Behind

The backend was Express.js and PostgreSQL. The task workers were Celery, which is Python. If you have never had to make those two talk to each other, the summary is that Celery is not a queue, it is a protocol with opinions.

A Celery worker does not just pull a JSON blob off Redis and run it. It expects a specific message envelope: task name, args, kwargs, an id, retry metadata, and a content-type the worker is configured to accept. So "just publish to Redis from Node" turns into "reimplement enough of the Celery message protocol to not get silently dropped."

The tradeoff is real and worth naming, because most people land on one of three answers:

1. **Publish Celery-protocol messages directly from Node.** Fastest path, no extra hop. The cost is that you now own a partial reimplementation of someone else's wire format, and it breaks when Celery changes it.
2. **Run a thin Python dispatch service.** Node calls it over HTTP, it calls `.delay()`. Correct by construction, since the real Celery client builds the message. Costs you a network hop and one more thing to deploy.
3. **Skip Celery entirely and use a Node-native queue.** Honest option. We didn't, because the work being queued was Python work.

The thing I would tell anyone starting this: pick deliberately, and write down why. The failure mode is picking option 1 by accident, because it looks like it works in development, and then discovering the gap in production when a message silently doesn't match what the worker expects.

## Keeping Typesense Honest

Search ran on Typesense, but PostgreSQL was the source of truth. That gap is the entire problem. A search index is a cache, and every cache is a lie that has to be actively maintained.

The rule I settled on is that the index is never written to directly by request handlers. Every change goes through a task. That gives you one code path to reason about, one place to add retries, and one place to fix things when the index drifts.

Two kinds of jobs, doing different work:

1. **Incremental updates**, fired when a row changes. Fast, small, and the thing that runs constantly.
2. **Bulk reindex**, which rebuilds from PostgreSQL. This is the one you actually need. Incremental updates will drift eventually, because tasks fail, deploys land mid-flight, and someone will run a migration that touches rows without going through the app. Being able to say "throw the index away and rebuild it" turns a scary class of bug into a boring operation.

The part that bites: a failed incremental update is invisible. Nothing 500s. A user searches, doesn't find the thing, and assumes it doesn't exist. There is no error in your logs because nothing errored. This is why the reindex job matters more than the incremental one, even though the incremental one does 99% of the work.

## Tracing Across the Queue Boundary

This is the piece I would keep in any system I build again.

An HTTP request is easy to trace, since the whole thing happens in one process and the context follows the call stack. A queue destroys that. The request finishes, returns 202, and the actual work happens somewhere else, minutes later, in a different language, in a different container. Your trace ends at the enqueue and a new unrelated trace starts at the worker. You have two halves of a story and no way to staple them together.

The fix is propagating trace context through the message itself. You inject the trace context at enqueue time, carry it as part of the task payload, and extract it in the worker so its span becomes a child of the request that queued it. Then one trace spans Express, Redis, and the Python worker, and you can finally answer "what happened to this specific user's action" instead of guessing.

We ran OpenTelemetry collectors as sidecars rather than pointing every service at a central endpoint. The reason is boring and good: the app talks to localhost, so instrumentation stops caring about network topology, and the collector handles batching, retries, and export. When the telemetry backend has a bad day, the sidecar absorbs it instead of your API threads blocking on a slow export call.

## Where the 40% Actually Came From

Not from the queue. Moving work off the request path makes the API *respond* faster, which is not the same thing as the system *doing* more work. That distinction matters and it took me a while to internalize.

The honest sequence was: instrument first, then look, then fix the thing the traces pointed at. Every time I guessed at the bottleneck before looking, I guessed wrong. The tracing work paid for itself here, because once spans crossed the queue boundary, the slow parts stopped being a mystery.

## What I'd Do Differently

Set up tracing before building the thing, not after. I built the system, then made it observable, then found out what was slow. Doing it in that order meant the first round of optimization was guesswork, and guesswork on a distributed system is just expensive superstition.

I would also write the bulk reindex job on day one instead of the day I needed it. Same for a dead letter queue. Both are things you build calmly when nothing is broken, or frantically when something is.
